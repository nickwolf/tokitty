# Qt update dialog and updater UI (design)

Issue: [#113](https://github.com/nickwolf/tokitty/issues/113), milestone v0.7.0 "Qt widget". Builds on the Qt settings windows from [#112](https://github.com/nickwolf/tokitty/issues/112) (spec `2026-10-11-qt-settings-windows-design.md`, which this one follows in structure) and the main widget from #111. The behaviour being ported is the in-app updater from #77: `update_dialog.py`, the `update_controller` and `update_check` wiring in `run_gui` (`__main__.py:445-553`), and the self-check in `frozen.py`. The issue text: the self-update path is the one where a regression strands users on an old build, and the release workflow's update rehearsal has to pass against a Qt build. Siblings that stay out: #114 (tray, macOS About panel), #115 (packaging the Qt build), #142 (Qt becomes the default, Tk code deleted).

Status: approved by Nick, 2026-10-13, with both open questions decided as proposed. A Codex review (gpt-6-sol, high) the same day found four defects and three wrong citations; they are folded in and listed in the review section at the end.

## Goal

Qt mode (`TOKITTY_QT=1`) gets everything Tk has for updates: the daily background check, the "Update to vX.Y.Z…" menu item, the Updates section of General (toggle, status pill, Check now), the confirm dialog with its progress, cancel and failure states, the handover to the new copy and the rollback when it doesn't start, and both hidden entries the handover uses, `--apply-update` and `--after-update <token>`. A frozen build that ships Qt passes its own `--self-check` in a way every already-shipped updater accepts.

## Scope and non-goals

In scope: a toolkit-free home for the dialog's and the menu actions' logic, a Qt dialog over it, a Qt handover host, the update wiring in `run_qt`, routing the two hand-off flags to `run_qt` in Qt mode, the update item in the Qt right-click menu, the Qt checks in `--self-check`, and a local rehearsal of a frozen Qt build.

Not in scope: any change to the update core (`update_controller.UpdateController`, `update_check.UpdateChecker`, `update_install`, `update_swap`, `updater`) beyond moving shared steps out of `TkHost`; any change to what the Tk path does; the tray and its "Tokitty vX is available" notification (#114); adding PySide6 to the frozen build and the CI rehearsal against it (#115); removing the Tk checks from `--self-check` (#142, but this spec fixes the rule #142 must follow, decision 7).

## Proposed decisions

1. **The dialog's logic and the menu actions move into a toolkit-free module, and Tk uses it too.** `update_dialog.py` keeps every rule inline in Tk methods: which buttons a refused or installable release gets (`:85-91`), the progress text (`:106-115`), what each outcome does (`:117-128`), the close policy while busy (`:130-132`), "check first when no release is in hand" and the single in-flight check (`:155-168`), and the result messages (`:174-186`). Copying them into a Qt dialog would give two copies of the updater's user-facing rules, on the one path where drift strands users. They move to `tokitty/update_flow.py` as two classes: `UpdateFlow` (one per dialog: holds the release, the controller and the refusal asked once, and drives a renderer through `show(note, buttons)` and `close()`, where `buttons` is a list of `(label, callback)`) and `UpdateActions` (`install()`, `check_now()`, taking `defer(fn)`, `error(title, text)`, `info(title, text)` and `offer(release)` hooks). The Tk `UpdateDialog` and `UpdateUi` become thin renderers over them with the same public surface (`open`, `alive`, `toplevel`, `note`, `button_labels`, `invoke`, `destroy`, `install`, `check_now`), and keep every Tk window property the dialog has today: `transient(root)`, which is what takes it away with the root when `TkHost.hide` withdraws it, the `WM_DELETE_WINDOW` protocol, `resizable(False, False)`, the title and colours. `tests/test_update_dialog.py` runs unchanged, but it checks buttons and reopening, not those properties, so slice 1 adds gui tests for them: the dialog's `wm transient` is the root, closing through the protocol is refused while busy, and withdrawing the root leaves the dialog unmapped. `RELEASES_URL` moves too and is re-exported. This is #112's decision 2 applied to the updater.
2. **The update core keeps its tick polling.** `UpdateController` and `UpdateChecker` do not use `worker_mailbox.Mailbox`: their workers write results under a lock and `tick()` hands them to callbacks on the GUI thread (`update_controller.py:358-370`, `update_check.py:125`). That is the same rule (a worker never touches a widget) by another route, and switching them to the mailbox would change the core Tk runs. So `run_qt`'s existing tick `QTimer` calls `updates.tick()` and `checker.tick()` first, as `run_gui`'s tick does (`__main__.py:480-482`), and drops its interval to 100 ms while `updates.busy`, as Tk does (`:517`). Nothing new goes on a `QtPoller`.
3. **A Qt handover host, sharing TkHost's toolkit-free steps.** The controller calls four host methods (`hide`, `restore`, `finish`, `notice`). `tokitty/qt/update_host.py` adds `QtUpdateHost` with the same four:
   - `hide`: set a `hidden` flag, then hide every visible top-level widget (`QApplication.topLevelWidgets()`) except the Stream Dock in-window views, remembering every one that is not a `QDialog` or a `QMenu` (registered or not: the presets form is an unregistered child window), then release the lock. Tk withdraws the widget's two Tk windows (`update_controller.py:126-132`); its dialogs are transient to them and go with them; the in-window views stay, as Tk never withdraws them. Covering every top-level rather than only the registered ones catches a modal `QMessageBox` (a hook warning, a check result) that is open while staging finishes: the tick `QTimer` keeps firing inside the box's nested loop, so the handover can start under it. Hiding a box inside `exec()` ends its loop as if dismissed (measured, PySide6 offscreen: `QMessageBox.warning` returned `NoButton` once a timer hid it), and it is not shown again by `restore`. While `hidden`, the tick leaves hook warnings queued in discovery instead of taking them, so no new box opens over a hidden app; they show after `restore`, or never if the new copy takes over and re-discovers. Update presentations (a check result, the dialog) go through `when_shown`, which holds them while hidden, replays them one loop turn after `restore`, and drops them on `finish`: staging can finish and hide the app in the same tick that delivers a manual check (Codex code review, 2026-10-13).
   - `restore`: the lock, runner relink and autostart steps of `TkHost.restore` (`:134-148`) move to a toolkit-free `update_controller.reclaim(lock, state_dir, backend)` that both hosts call; then the windows `hide` remembered show again, the registered ones with the stacking hint re-applied, and `hidden` clears. No tray to restart until #114.
   - `finish`: `QTimer.singleShot(0, app.quit)`. Safe twice, as Tk's is.
   - `notice`: deferred with `QTimer.singleShot(0, ...)` and shown through `QtHost.warn`, suppressed when quiet (`--apply-update`).
   `run_qt` already releases the lock in its `finally` (`qt/app.py:162`), after `hide` released it on a successful handover; `SingleInstanceLock.release` is a no-op on an unheld lock (`lock.py:50-52`), which is what `run_gui` relies on too (`__main__.py:566`).
4. **The Qt dialog is a top-level window under the stacking rules.** `tokitty/qt/update_dialog.py`, `QtUpdateDialog.open(host, release, running, controller)`: a parentless `QWidget` titled "Update Tokitty", fixed size, styled with the #112 kit, registered with `QtHost` before its first show and forgotten when it closes, one per process (reopening raises it, as `UpdateDialog.open` does, `update_dialog.py:24-37`). It renders `UpdateFlow`: the info line, the note wrapped at the same 340 px, and a row of buttons rebuilt on each `show`. Its `closeEvent` ignores the close while `UpdateFlow` refuses it (the controller is busy), as the Tk `WM_DELETE_WINDOW` handler does. Release notes opens through `webbrowser.open`, as Tk does. The check-result boxes (`QMessageBox.critical` and `information`) are deferred with `QTimer.singleShot(0, ...)` and parented as `QtHost.warn` parents, because they arrive from `tick()` and must not stall it (`update_dialog.py:170-172`).
5. **Qt gets the update item in its right-click menu, and no notification.** The Qt menu is the shared `build_menu`, which already places the item first when given `update_available_label` and `on_install_update` (`menu.py:46-51`); `run_qt`'s `menu_model` (`qt/app.py:300-310`) passes them. The menu is rebuilt each time it opens, so the label is always current. `announcer` (`update_check.py:194`) needs a tray; Qt passes a stand-in whose `refresh` is `QtHost.notify_state_changed` (so an open Settings pill updates) and whose `notify` returns False, which by design leaves `notified_tag` unwritten so the #114 tray announces the release on a later run. `QtHost` gains `on_install_update` next to the four update seams it already holds as `None` (`qt/host.py:43-46`); `run_qt` sets all five, and the General tab's Updates section appears with no change to `qt/settings.py`.
6. **Both hand-off flags reach `run_qt` in Qt mode.** Today `main` sends `--after-update` and `--apply-update` to `run_gui` even with `TOKITTY_QT=1` (`__main__.py:620-627`), with a comment deferring to this issue. The handover launches the new copy with the old copy's environment through `child_env` (`update_install.py:121-135`), so a Qt install relaunches into Qt mode once routing follows the flag. `run_qt` gains `after_update_token` and `apply_update` parameters and does what `run_gui` does with them:
   - `--after-update`: `acquire_with_retry(lock, 30)` instead of `acquire()`, silent on failure (`__main__.py:147-156`); exit 0 straight after taking the lock under `skips_ack` (`:157-159`); no walkthrough and no first-run mark (`:171-175`); after `app.exec()` starts and the widget is exposed, `write_ack`, polling every 50 ms up to 5 s for the exposure as `send_ack` polls for the map (`:527-544`).
   - `--apply-update`: no walkthrough; the host is quiet; `start_apply_newest` after startup; the exit code is 0 installed, 2 rolled back, 1 otherwise, and a non-installed outcome prints its message and calls `finish` (`:546-553`).
   - Both: `updates.startup(frozen=...)` on every launch, after the lock is held, as `run_gui` does (`:526`), which clears a stale `pending` and starts the cleanup thread in a frozen build. Qt mode skips it today.
   Without `TOKITTY_QT=1` nothing changes, and `tests/test_qt_launch.py:41-47`, which pins today's routing, is updated to the new rule.
7. **The self-check reports Qt, and keeps the `tk_root` key every shipped updater requires.** The old copy judges the new one by its `--self-check` report, and every build shipped so far refuses a report without a `tk_root` entry or with any failed entry (`update_install.py:390-395`). That code is frozen into users' installs and cannot change. So:
   - Which toolkits a build carries is declared, not guessed. The runtime hook that bakes `TOKITTY_BUILD_ID` (`freeze/tokitty.spec:30-36`) also bakes `TOKITTY_BUILD_TOOLKITS`, from the variable of the same name at build time, default `tk`. A source run reads the variable from its environment, with the same default. Gating on "PySide6 is importable" was the first draft and is wrong both ways: PyInstaller can collect PySide6 from a build venv that merely has it installed, and then a broken Qt platform plugin would fail a Tk build that works, which every shipped updater refuses; and a Qt build whose PySide6 failed to import would skip its own check.
   - `frozen.self_check` gains `qt` (import `PySide6.QtWidgets`, report the Qt version) and, under the same `TOKITTY_SELF_CHECK_TK=1` switch as `tk_root`, `qt_root` (a `QApplication` on the real platform plugin, one widget shown and its events processed, then closed), both present exactly when the declaration names `qt`. `tkinter` and `tk_root` stay exactly as they are when it names `tk`, so a build made with the default reports what it reports today. #115 builds with `tk,qt`.
   - The rule for #142: a build whose declaration lacks `tk` still emits `tk_root`, carrying the `qt_root` result, and emits no `tkinter` entry, or every update from v0.6.x and earlier to it fails at the self-check. With the declaration in place this is a few lines and one test, so #113 implements it (open question 1).
8. **The rehearsal against a Qt build runs locally now and in CI with #115.** There is no frozen Qt build until #115 adds PySide6 to the bundle. `freeze/verify_update.py` builds each child's environment from the caller's (`scratch_env`, `verify_update.py:640`, over `verify_artifact.py:200-208`), dropping only `TOKITTY_UPDATE*`, `SSL_CERT_FILE` and `PYINSTALLER_RESET_ENVIRONMENT`, so `TOKITTY_QT=1` drives the old copy's `--apply-update` and the new copy's `--after-update` through `run_qt`. Its checks (exit code, ack consumed, one GUI process holding the lock) do not show that a window appeared, and the ack is written even when the exposure wait times out, as Tk's is after its 5 s map wait. So the Qt `--after-update` path records whether the widget was exposed before the ack in `after-update-qt.json` in the state dir, written only when `TOKITTY_UPDATE_API_URL` is set, the gate `skips_ack` already uses (`update_controller.py:89-93`), so a real install never writes it (a stderr line would be lost: the new copy is launched with its output on `DEVNULL`, `update_swap.py:273`), and the rehearsal must run on a real platform plugin: `QT_QPA_PLATFORM` unset (an inherited `offscreen` would let both copies pass with nothing on any display). Before the PR, build v0.0.1 and v0.0.2 bundles on Linux from this branch with PySide6 in the build venv, `TOKITTY_BUILD_TOOLKITS=tk,qt` and a local, uncommitted spec change that collects PySide6, and run `verify_update.py --rehearsal` under `xvfb-run` with `TOKITTY_QT=1` and `QT_QPA_PLATFORM` unset; every step must pass and the `apply_update` scenario's state dir must hold `after-update-qt.json` saying the widget was exposed before the ack. The report goes in the PR description. #115's acceptance gains the same run in CI on Windows, macOS and Linux, with that file checked by the verifier.

## The shared flow

`tokitty/update_flow.py`, no toolkit imports.

`UpdateFlow(release, running, controller, render, open_url)` where `render` has `show(note, buttons)` and `close()`. On construction it asks `controller.refusal(release)` once (it writes a probe file, `update_controller.py:248-250`) and shows the choices: a refusal shows only "Open release page", an installable release shows Install and Release notes, and both add Later (`update_dialog.py:85-91`). `install`, `cancel`, `on_progress`, `on_done` and `close_requested` carry the Tk methods' rules and texts exactly, including "An update is already in progress.", "Preparing…", "Cancelling…" with no buttons, progress ignored once cancelling, "Updated to vX. Restarting…" with no buttons, close on `rolled_back` (the controller's notice says what happened), and "Cancelled." or the failure message over the choices again. `alive` goes False on close, and late callbacks are ignored, as now.

`UpdateActions(checker, controller, defer, error, info, offer)`: `install()` offers the known release or checks first; `check_now()` ignores a second click while a check is in flight; the result is deferred, then shows "Couldn't check for updates: …", offers the release, or says "Tokitty X is the latest version." with the titles Tk uses (`update_dialog.py:174-186`).

Both are tested without a toolkit against a fake controller and checker. The Tk `gui` tests stay as they are.

## run_qt changes

In `_run_locked`, which gains the lock and the two flags as parameters:

1. Classify the first run with the hand-offs excluded, as `run_gui` does.
2. After `make_controls`, build `QtUpdateHost(app, host, lock, state_dir, controls.autostart_backend, quiet=apply_update)`, then `UpdateController(state_dir, update_host)`, `UpdateChecker(state_dir, updates.running, enabled=..., on_available=announcer(state_dir, stand_in))` with the same plain `{"on": settings.update_check}` shadow state and toggle (`__main__.py:459-469`), and `UpdateActions` with Qt hooks. Set the five seams on `QtHost`.
3. The tick calls `updates.tick()` and `checker.tick()` before the rest, and sets the timer interval from `updates.busy` at its end.
4. `updates.startup(...)` after the pollers start, then the ack timer or `start_apply_newest`, then `app.exec()`. The return value is the apply exit code under `--apply-update`, else 0.
5. The `finally` gains nothing: the controller's threads are daemons, and an open update dialog is closed with the application.

The debug-state launch (`qt/app.py:236-266`) keeps no updater, as now.

## Tests

The `qt` marker and CI job from #111 carry the Qt tests; plain `pytest` stays headless.

Unmarked:

- `UpdateFlow`: every branch the Tk gui tests cover today, with a fake controller and a recording renderer: choices for refused and installable releases, install refused while busy, progress texts at 0, partial and full totals, cancel and late progress, each outcome, close refused while busy, callbacks after close ignored.
- `UpdateActions`: known release offered, unknown release checks first, a second `check_now` while one is in flight does nothing, each result message, results deferred through `defer`.
- `update_controller.reclaim`: lock retried, relink and autostart failures printed and not raised, `TkHost.restore` still calls the steps in the same order (the existing `test_update_controller.py` handover and rollback tests run unchanged).
- `frozen.self_check`: with the default declaration the report has exactly today's keys whether or not PySide6 is importable; with `tk,qt` it adds `qt`, and `qt_root` only with `TOKITTY_SELF_CHECK_TK=1`; with `qt` alone it has no `tkinter` entry and its `tk_root` carries the `qt_root` result; a declared `qt` with PySide6 blocked fails `qt`. The existing `tk_root` tests stay. `run_self_check` accepts each of those reports (the shipped judge, run against them).
- Routing: with `TOKITTY_QT=1`, `--after-update <token>` and `--apply-update` call `run_qt` with the right arguments; without it they call `run_gui` as today.
- Isolation: `update_flow`, `update_controller`, `update_check` and `updater` join `_MODULES`, and `qt/update_dialog.py` and `qt/update_host.py` join `_QT_MODULES` (`tests/test_toolkit_isolation.py:17-66`).

Marked `qt`, offscreen:

- Dialog: opens with the right buttons for refused and installable releases; reopening raises the one window; Install, progress, Cancel and each outcome drive the note and buttons as in Tk; the close event is ignored while busy; registered for stacking, and toggling Always in front sets the hint on it; forgotten after close.
- Host: `hide` hides the widget and the visible registered windows and releases a fake lock; a `QMessageBox` open in its own `exec()` when `hide` runs is closed and not restored; the tick takes no hook warnings while hidden and takes them after `restore`; `restore` shows exactly those again, reacquires, and keeps the stacking hint; `restore` with the lock held elsewhere raises and leaves the windows hidden; `notice` is deferred and silent when quiet; `finish` twice quits once.
- `run_qt`: a fake controller and checker in a world built like `make_world`; the menu shows "Update to vX…" first only while the checker knows a release; General shows the Updates rows and the toggle writes `settings.json`; Check now with each result shows the right box (patched); the tick interval is 100 ms while busy.
- Hand-offs: `run_qt(after_update_token=...)` in a subprocess with a scratch state dir writes the ack once the widget is exposed and does not show the walkthrough on a fresh dir; with `skips_ack` it exits 0 without an ack; `run_qt(apply_update=True)` with a fake controller returns 0, 2 and 1 for the three outcome groups.
- `tests/qt/test_host.py:19-24`, which asserts the update seams are `None`, changes to assert they are `None` on a bare `QtHost` and set after `run_qt`'s wiring.

Manual, Windows (Cucumber, 100% and 150%), from source with `TOKITTY_QT=1` and a scratch `LOCALAPPDATA` only (the `C:\tmp\qt112-launch.ps1` pattern), never the real state dir: with `TOKITTY_UPDATE_API_URL` at a local fake release feed, the right-click menu shows the update item, the dialog comes up in front of the widget with Always in front on and off, and Check now from General shows the latest-version box. A source run is not installable (`RunningVersion.installable`), so the dialog shows the refusal; the install path itself is covered by the rehearsal (decision 8).

## Slices

1. Shared flow: `update_flow.py`, the Tk dialog and `UpdateUi` on it with re-exports, `update_controller.reclaim` with `TkHost.restore` on it, their unmarked tests, isolation entries. Touches the Tk path, so it lands with the gui tests passing unchanged.
2. Qt dialog and host: `qt/update_dialog.py`, `qt/update_host.py`, `QtHost.on_install_update`, their `qt` tests. Depends on 1.
3. `run_qt` wiring and routing: the checker, controller and seams in `_run_locked`, the menu item, the tick, `startup`, both hand-off flags, the `main` routing change, the hand-off tests. Depends on 2.
4. Self-check: `TOKITTY_BUILD_TOOLKITS` in the runtime hook and in `frozen.py`, the `qt` and `qt_root` checks, the `tk_root` rule for a build without `tk`, and their tests. Independent; can run beside 1 to 3.
5. Local rehearsal (decision 8), after 3 and 4. No committed code unless it finds a defect.

Proposed: one PR for all five, since slice 1's Tk change is a behaviour-preserving move whose proof is the unchanged gui suite, unlike #112's slice 1, which changed state writes real users run.

## Review (Codex, 2026-10-12)

gpt-6-sol at high effort, read-only, briefed cold. Every claim was checked against the code before changing anything here, and all held. What changed:

1. Self-check gating: the Qt checks follow a baked `TOKITTY_BUILD_TOOLKITS` declaration instead of whether PySide6 imports. The draft would have let a Tk build that happened to collect a broken PySide6 fail a check every shipped updater treats as fatal (`update_install.py:389-395`).
2. Rehearsal: it runs with `QT_QPA_PLATFORM` unset, and the new copy records (in a test-gated file) whether its widget was exposed before the ack, since the verifier's process and ack checks pass for an invisible window.
3. Handover with a modal box open: `hide` covers every top-level widget, which ends a box's nested loop (measured), and hook warnings wait while the app is hidden.
4. Tk dialog properties: the renderer keeps `transient(root)` and the close protocol, and slice 1 tests them, because the existing gui tests would pass without them.

Citations corrected: the environment pass-through is `scratch_env` at `verify_update.py:640`, not `verify_artifact.py:201` alone; the routing test is `test_qt_launch.py:41-47`; the seam test runs to `test_host.py:24`. Codex also confirmed the lock release and reacquire order, and that `verify_update.py`'s process checks are toolkit independent.
