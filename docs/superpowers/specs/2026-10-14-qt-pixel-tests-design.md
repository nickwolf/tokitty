# Pixel-exact reference images for the Qt widget (design)

Issue: [#128](https://github.com/nickwolf/tokitty/issues/128), milestone v0.7.0. The issue text: turn the #109 spike's 0-mismatch comparison of the drawn cat against `raster_rgba` into a CI job on Windows, macOS and Linux with `QT_QPA_PLATFORM=offscreen`; keep reference images for every state and coat at dpr 1 and 2, plus a few widget layouts (default card, low opacity, cat on top, cat beside); fail on any pixel difference; make updating a reference a deliberate step that shows the diff, so an art change in #125 shows exactly which pixels moved.

Inputs: the #109 spike findings (`2026-10-10-pyside6-spike-findings.md`, section 1), the #111 spec (`2026-10-11-qt-main-widget-design.md`), the #142 spec (`2026-10-14-qt-only-design.md`, decision 3 on the Stream Dock renderer). Written against main at 3d57edd (#142 merged as PR #154).

Status: draft reviewed by Codex (gpt-6-sol, high) on 2026-10-14; its seven findings and what changed are in the review section at the end. "Cat beside" in the issue predates the 2026-10-12 spot revision; the spots are now `inside`, `inside_right` and `on_top`, so the layouts here use those.

## Goal

A `qt`-marked test module compares the widget's real paint output, taken with `grab()`, against PNG references in the repo, on all three CI systems, and fails on any differing pixel outside the regions this spec masks. One command regenerates the references and prints, for every file, how many pixels changed and where, and writes an old/new/difference image for each changed file.

## Facts this design rests on

Measured on 2026-10-14 with PySide6 6.12.0, locally (WSL Ubuntu and native Windows 11 on an Intel i7-9700KF) and in CI on the draft probe PR #159 (runs 38667297202 and 38667685717; the Linux and Windows runners reported an AMD EPYC 7763, the macOS runner an Apple M1 (Virtual)). The probe hashed RGBA bytes of plain text, Stream Dock keys and widget grabs at `QT_SCALE_FACTOR` 1 and 2.

1. **Windows offscreen draws text once an application font is registered.** With no application font it has no families and draws nothing (the #111 lesson). After `QFontDatabase.addApplicationFontFromData` with the bundled Aileron it reports one family and draws with it, including for a `QFont()` with no family (it falls back to the only family there is).
2. **Linux and Windows rasterize Aileron identically only with an explicit hinting preference and no subpixel antialiasing.** With the default hinting preference the two differ (Windows behaves as `PreferFullHinting`, Linux as vertical hinting through fontconfig): 883 against 899 inked pixels for the same string. Setting `PreferFullHinting` (or `PreferNoHinting`) made standalone text byte-identical. Inside the widget it still differed, because on Linux the widget's text came out with subpixel (LCD) antialiasing, visible as colour fringes, and on Windows greyscale. Adding `QFont.StyleStrategy.NoSubpixelAntialias` made all four probed card layouts (default, `inside_right`, `on_top`, 20% opacity) byte-identical between Linux and Windows at scale 1 and 2, locally and on the CI runners.
3. **macOS rasterizes text differently and no setting changes that.** macOS offscreen goes through CoreText: all four hinting preferences gave the same hash, and `QT_QPA_PLATFORM=offscreen:fontengine=freetype` changed nothing. Every pixel that differed between macOS and Linux in the default and 20% cards lay inside a text box widened by 2 px; outside them the grabs were identical, the cat included.
4. **Text over a translucent card differs by CPU.** The 20% card differed in 18 pixels, each channel by at most 1, between the local Intel machine and the EPYC runners, while Linux and Windows on the same machine agreed with each other (both locally and in CI). The default, `inside_right` and `on_top` cards (text on an opaque card) were identical across both CPUs. The differing pixels are glyph edges whose destination alpha is below 255. The probe used the default theme, whose halo is off (`TextStyle.halo = "off"`), so no halo was drawn in it. The likely cause is an approximate reciprocal in Qt's unpremultiply path, which Intel and AMD compute differently; that is not proven, and `QT_NO_CPU_FEATURE` is not honoured by this Qt build (disabling `sse2` changed nothing), so it cannot be switched off.
5. **The cat is exact everywhere.** The #109 spike already showed 0 mismatched pixels against `raster_rgba` from 100% to 200%; the probe adds that the cat region of the card is byte-identical on all three systems and both CPUs. `_cat_image` rasterizes at `cell = round(4 * dpr)` and sets the image's dpr, so at dpr 2 the cat is exactly the dpr 1 cat scaled up 2x with nearest neighbour.
6. **The art.** 14 states (`sprites.ALL_STATES`), 2 frames each except `flopped` with 4, so 30 frames; 6 colourways and 9 patterns, so 54 coats; the five legacy coat names map onto these. A frame is 28x26 sprite pixels, 112x104 at dpr 1.
7. **Sizes.** One sheet per state with every coat as a row and every frame as a column, written as an exact-palette indexed PNG (at most 38 colours per sheet, round-trip checked to give back the same RGBA bytes): 14 files, 221,572 bytes at dpr 1 and 506,270 more at dpr 2. As RGBA PNGs the same sheets were 511,899 and 914,639 bytes. The probed card grabs were 6,184 to 7,204 bytes at scale 1 and 15,443 to 18,169 at scale 2; Stream Dock keys about 1,000 to 1,600 bytes each.
8. **The Stream Dock keys are not the same on every OS today.** `render.py`'s docstring says the bundled font makes the keys "look the same on every OS", but `_font` leaves the hinting preference at its default, so the status and usage keys differ between Linux and Windows (fact 2). With `PreferFullHinting` and `NoSubpixelAntialias` they are identical, and the Linux keys become the Windows keys.

## Decisions

1. **Card text uses the bundled Aileron in these tests, with explicit hinting and no subpixel antialiasing; per-OS references and masking all text are both rejected.** The test widget is a subclass that overrides one new method, `TokittyQtWidget._make_font(points, bold)`, which `_font_set` calls for each of its three fonts; the product method keeps today's behaviour (Segoe UI on Windows, the platform default elsewhere). The test override returns Aileron with `setPixelSize(round(points * 96 / 72))` (12 px for the 9 pt label, 11 px for the 8 pt texts), `PreferFullHinting` and `NoSubpixelAntialias`, so the size does not depend on the platform's logical DPI. Why: facts 1 and 2 give one shared reference set that checks text placement, alignment, wrapping, colour and the halo on Linux and Windows. Per-OS references would triple the set and the Windows ones would need text anyway. Masking all text would lose the layout checks the issue is asking for. What this does not test is the product's own fonts, which differ by OS and font stack by design and cannot be pixel-exact. The product's fonts are not changed here; whether the card should also turn off subpixel antialiasing on Linux (it draws onto a translucent window, where LCD antialiasing is questionable) is a separate question, left out of scope.

2. **Text is masked where facts 3 and 4 say it must be, and nowhere else.** All of the widget's text goes through `_text` (the status text and account label, which call `p.drawText` directly today, move onto it; the tag chip text already does or moves too). The test wraps `_text` to record, for each call, the rect the text actually occupies (`p.boundingRect(rect, flags, text)`), mapped through the painter's transform. The mask is the union of those rects widened by 2 logical px on every side (the halo reaches 1 px). Using the occupied rect, not the layout rect, matters: the status box runs to the card's right and bottom edges, so masking it would hide card pixels. `update` stores each card reference's text rects in a small JSON sidecar, and the test masks the union of the reference's rects and the live render's: on macOS the status line came out narrower than the Linux reference (CI run 38675418255, 30 pixels at dpr 1 just past the end of the macOS text), so a mask from the live rects alone left reference glyphs exposed. Codex predicted this in its review of slices 1 and 2. Masked pixels are set to a fixed colour in both the grab and the reference before comparing. The mask applies on macOS to every layout (fact 3), and on every system to text drawn over a card whose alpha is below 255, which today means the low-opacity layout (fact 4). Outside the mask every pixel must match. Each masked layout records its mask in the failure output so a reviewer sees what was not compared.

3. **Cat references: one indexed PNG sheet per state, at dpr 1 and at dpr 2.** Each sheet has the 54 coats as rows in `COLORWAYS` x `PATTERNS` order and the state's frames as columns, transparent background. It is built from widget grabs, not from `raster_rgba`: a one-pane widget with the cat `on_top`, so the cat sits over the transparent margin with nothing else drawn under it; for each coat and frame the test sets the pane's palette, state and frame and grabs the cat rect. The dpr 2 sheets are grabbed in a subprocess with `QT_SCALE_FACTOR=2`, as `test_cat_pixels_dpr2_in_a_subprocess` does today. Both sets are stored, as the issue asks. Fact 5 means the dpr 2 sheet carries no information the dpr 1 sheet lacks, and I first proposed deriving it to save 506,270 bytes; the review pointed out that this quietly drops a stated requirement for a modest saving, so the files stay. `update` and the CI diff report (decision 9) list the dpr 1 and dpr 2 file of a state together. 1,620 grabs at dpr 1 took 2.45 s locally. The mirrored cat (`inside_right`) is covered by its layout reference. Legacy coat names are not separate rows; they resolve to rows that are already there.

4. **Layout references.** Six layouts, each at dpr 1 and dpr 2 as separate files (text and antialiased card corners are not a 2x scale of dpr 1): the default card (`inside`, 100% opacity, both bars, reset text, a status line and an account label); the default card with the halo set to `on` (opaque, so the halo is compared unmasked on Linux and Windows; a halo colour or offset change fails here); the card at 20% opacity with the halo set to `auto` explicitly (the default theme has it off), masked per decision 2; the cat `inside_right`; the cat `on_top`; and the models view (`render_usage`). Tag strings are empty in every layout and in the cat sheets: a non-empty tag chip paints into the `on_top` cat rect. All inputs are fixed (no clock, no randomness; the frame timer is stopped and frames are advanced with `draw_next_frame()`). Twelve RGBA PNGs, about 130 KB.

4a. **The product fonts get a fit check, not a pixel check.** Decision 1 means a product font change (size, family, the Windows Segoe UI override) cannot move a reference. A separate `qt`-marked test builds the default and models layouts with the real `_font_set` and asserts, on each OS, that every text's occupied rect lies inside the card and that the status line wraps to at most two lines. This catches clipping and runaway wrapping with the shipped fonts without pretending their pixels are portable.

5. **Stream Dock keys get references, and `render._font` gets the same two font settings.** `_font` sets `PreferFullHinting` and `NoSubpixelAntialias`, which makes the docstring's promise true on Linux and Windows (fact 8). This is a visible product change on Linux: its keys' text becomes today's Windows rendering (crisper stems, slightly different glyph widths). macOS keys are unchanged, and the docstring is corrected to say the keys match on Linux and Windows and use the same font on macOS. References: a session key (one state, one coat, a title, with and without accent), the usage key (normal and `warn`), every decision kind armed and the two that can be disarmed, a one-word and a multi-word status key, and a set of preview keys. About 14 files of about 1 to 2 KB. They are compared on Linux and Windows. On macOS the key tests skip with the reason in the message: CoreText renders the text differently (fact 3), the keys are mostly text, and the cat on the session key comes from the same `raster_frame` the cat sheets prove on macOS. The existing renderer tests stay.

6. **Where things live.** References in `tests/qt/pixel_refs/` (`cat/<state>.png`, `card/<layout>@<dpr>x.png`, `keys/<name>.png`), outside the `tokitty` package so they never reach a wheel or the frozen bundle, with a `.gitattributes` line marking them binary. Shared code (building the test widget, grabbing, masking, comparing, writing diff images) in `tests/qt/pixel_check.py`, which the test module imports the way `test_widget.py` imports `cat_check.py`. Reading and writing PNGs uses Pillow (a dev dependency already); comparison is on RGBA8888 bytes.

7. **Updating a reference is one explicit command.** `python tests/qt/pixel_check.py update [name ...]` renders the current output, compares it with the stored references, prints one line per file (`unchanged`, `new`, or the number of changed pixels and their bounding box), writes `old | new | difference` images for the changed files into `build/pixel-diff/` (gitignored), and only then writes the new references. Without names it updates everything. It refuses to run on macOS (fact 3: macOS output is never the reference). It runs on Linux or Windows. The measurements cover two CPUs (one Intel, one AMD) and one runner image per OS; the only CPU-sensitive pixels found are inside the low-opacity layout's mask, but that does not prove every future runner CPU, image or Qt build renders the rest identically. So `tests/qt/pixel_refs/README.md` records the PySide6 version and the machine and OS the references were last made on, and says to treat a CI mismatch that no code change explains as possible environment drift (rerun, compare the CPU in the job log, look at the diff image) before updating anything. A new translucent paint case (a tag chip, an antialiased edge over a translucent card) is measured on both CPU vendors before its reference is trusted unmasked. The test suite itself never writes references, whatever the environment.

8. **A failure shows the diff.** When a comparison fails, the test writes the actual image, the reference and the difference image into `build/pixel-diff/` (or `$TOKITTY_PIXEL_DIFF_DIR`), and the assertion message gives the file, the number of differing pixels, their bounding box and the first few coordinates with both colours. The `qt` CI job uploads `build/pixel-diff/` as an artifact when the job fails, so a failure on a system nobody has locally (macOS) can be looked at.

9. **CI.** The tests are `qt`-marked and run in the existing `qt` job on all three systems, which gains the artifact upload from decision 8. On pull requests, the Linux `qt` job also runs `python tests/qt/pixel_check.py report <base sha>`, which reads every reference PNG that differs from the PR's base commit (`git diff --name-only`, old bytes through `git show`), writes old/new/difference images to `build/pixel-report/`, uploads them as an artifact whether the job passes or fails, and appends one line per changed file (pixels changed, bounding box) to `$GITHUB_STEP_SUMMARY`. That is what a reviewer of a #125 art PR opens; the local `update` output is only for the person making the change. The checkout needs `fetch-depth: 0` (or a fetch of the base) for `git show` to find the base. The probe step from PR #159 and `tests/qt/probe_128.py` are removed before the PR is ready.

10. **The existing cat tests stay.** `test_cat_pixels_dpr1` and the dpr 2 subprocess test compare the grab with `raster_rgba` live, which proves the paint path against the art source; the references prove the art did not change. They test different things.

11. **PySide6 is pinned exactly (`==6.12.0`), so references are tied to that version.** A Qt bump that changes rasterization fails these tests; the fix is to run `update`, look at the diff images, and commit them with the bump.

## Slices

1. **Product seams and the key font.** `_make_font` and the `_text` routing in `tokitty/qt/widget.py`; `_font` settings in `tokitty/streamdock/render.py`; their unit tests. Small; no references.
2. **Harness, cat sheets and layouts.** `tests/qt/pixel_check.py`, the test module, the `update` command, the cat sheets and layout references, the masking, the failure output, `.gitattributes`, `.gitignore`. Depends on slice 1.
3. **Stream Dock key references and CI.** Key references and their tests, the product-font fit check (decision 4a), the `report` command and the CI steps (decision 9), the failure artifact upload, removal of the probe, `tests/qt/pixel_refs/README.md` with the update and triage procedure. Depends on slice 2.

## Verification

- `pytest -m qt` passes locally (WSL) and on native Windows from the worktree, and on all three CI systems.
- A deliberate one-pixel change to one sprite template fails exactly the matching cat sheet on all three systems, at dpr 1 and dpr 2, with a diff image that shows the moved pixels; `update` then reports that file and only that file with the expected count. The change is reverted.
- A deliberate colour change to a bar fails the default layout on all three systems, macOS included (outside the mask). A deliberate change to the halo colour fails the halo-on layout on Linux and Windows.
- The PR's own CI run shows the `report` summary listing every added reference as new.
- `update` run twice in a row reports every file `unchanged` the second time.
- The reference files are absent from the wheel (`pip wheel .` and list it).

## Out of scope

Pixel tests for the Settings, accounts, walkthrough, update and permission windows; real-display (non-offscreen) grabs; fractional dprs (the spike covered 125% to 200% against `raster_rgba`, and the existing tests keep that); turning off subpixel antialiasing in the product card on Linux; the art changes themselves (#125).

## Codex review (2026-10-14)

gpt-6-sol at high effort, read-only, on the draft at 1fa6892. Findings in its order, with what changed.

1. High: the low-opacity layout did not test the halo, because the theme default is `halo="off"` (confirmed in `theme.py:92`), and a halo there would be masked anyway. Fixed: the low-opacity layout sets `auto` explicitly, and a new opaque halo-on layout compares the halo unmasked (decision 4); verification updated.
2. High: masking the status layout rect hides card pixels, since that rect runs to the card's right and bottom edges. Fixed: the mask uses the rect the text occupies (decision 2). Codex's alternative, a second text-free render per layout, was not taken: it doubles the layout files to recover only the card pixels directly under glyphs on macOS.
3. Medium: the claim that references can be made on any CPU went beyond two measured hosts. Fixed: softened, with recorded versions and a drift triage step (decision 7).
4. Medium: the test font hides layout regressions with the real fonts. Partly taken: a fit check with the product fonts on each OS (decision 4a); their pixels stay untested by design.
5. Medium: deriving dpr 2 drops the issue's stated requirement. Taken: dpr 2 sheets are stored (decision 3).
6. Medium: after a successful update nobody reviewing the PR sees the diff. Fixed: a `report` step on every PR publishes the diff images and a summary (decision 9).
7. Low: the key font change alters Linux keys and macOS keys stay uncompared. The Linux change is now stated plainly and the docstring corrected (decision 5); the macOS skip stays, because a text-free key layer would test little beyond the cat, which the sheets cover.

Checked and found sound by the review: the `on_top` cat rect is clear when tags are empty (now required, decision 4); state and frame can be set through `render()` and `draw_next_frame()` without private access; the Bash CI shell handles `build/pixel-diff/` on Windows and `build/` is ignored; PySide6 is pinned.
