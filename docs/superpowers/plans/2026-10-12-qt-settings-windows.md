Spec: `docs/superpowers/specs/2026-10-11-qt-settings-windows-design.md`. Slice 1 (the toolkit-free groundwork) is PR #144. This plan covers slices 2 to 5, which go in a second PR. Branch `qt-windows-112`, worktree `.worktrees/qt-windows-112`, cut from `qt-settings-112`; once #144 merges with `--no-ff`, merge main into it (the slice 1 commits are identical, so nothing conflicts). Read the spec before each slice; this plan orders the work and pins what the spec leaves to implementation.

The Tk windows are the behaviour to match. Each slice ports one or more of them, so its implementer reads the Tk module whole before writing the Qt one, and keeps the Qt module's structure parallel to it (same class names, same method names where the method still makes sense), so a reviewer can read the two side by side.

## Slice 2: kit, poller, host, Settings with General, Look, Theme and Usage

Files: new `tokitty/qt/kit.py`, `tokitty/qt/poller.py`, `tokitty/qt/host.py`, `tokitty/qt/settings.py`, `tokitty/qt/widget.py` and `tokitty/qt/pane.py` (small additions), `tokitty/qt/app.py`, new `tests/qt/test_kit.py`, `tests/qt/test_settings.py`.

1. `qt/poller.py`: `QtPoller(owner, mailbox, handler, keep_alive, on_tick=None, interval_ms=120)`, the counterpart of `settings_async.Poller` (read it): a single-shot `QTimer` parented to `owner`, re-armed each tick. Each tick, in Tk's order: drain the mailbox and call `handler(tag, ok, value)` for each entry, stop if cancelled meanwhile, call `on_tick()` if given (even with no result: the Accounts tab uses it to notice the manager closing and the hook guard being released, the walkthrough for its spinner), then re-arm while `keep_alive()` is true. `cancel()` stops the timer and drains the mailbox, dropping stale results, as Tk's does. Tests: results put from a worker thread are delivered on the GUI thread, in order; `on_tick` runs on an idle tick; `cancel` stops delivery and empties the mailbox.
2. `qt/kit.py`: `Kit` with the method names of `settings_widgets.Kit` (`page_header`, `section_header`, `button` with every style Tk has, including `quiet`, and `compact`, `toggle` with its `compact` option, `pill`/`set_pill`, `segmented`, `dropdown`, `entry`/`set_entry_error`), plus `rail(entries, version)` and `sprite_preview(palette, state, mirrored)`. Widgets are `QWidget` subclasses with the same small API as their Tk counterparts (`Toggle.set/get/set_enabled`, `Segmented.set/get`, `Dropdown.set/get/set_choices`). Colours and fonts from `settings_style`. Styling is one style sheet built from those constants and set on each top-level window this issue creates (`Kit.style_sheet()`), never on the `QApplication`. Sizes are logical pixels; `Kit.px` is the identity. The sprite preview draws through `sprite_raster.raster_rgba` into a `QImage`, mirrored when asked. Tests: each control's `on_change` fires on a click and not on `set()`; `set_entry_error` toggles a property the style sheet reads; the preview's opaque pixels match `raster_rgba`.
3. `qt/pane.py`: `QtPane.set_customization(custom, label=None)`, which replaces the pane's whole `Customization` (so `cat_home` survives and a reset really clears old overrides), recomputes palette, colorway and pattern from it, and repaints. It never derives the shown label from `custom.label`: launch shows `unit["label"]` from `app_core.initial_label` (`qt/app.py:176-178`), which differs from `custom.label` for an unnamed account, so the pane keeps its current `_label` unless `label` is passed. `qt/widget.py`: `set_theme(theme)` swaps the theme, clears `_layouts` and the image cache, recomputes homes with `theme.resolve_home` and calls `rebuild_layout(homes)` when they changed, then `update()`; `pane_anchor(index)` returning the window position plus `pane_origins[index]` plus 16 (used in slice 5); and `closeEvent` calling `QApplication.quit()`. Tests: a Cat sits change followed by a colour change keeps `cat_home`; `set_theme` with a new opacity changes the card alpha at a sampled pixel; after `set_theme`, the window size still equals `theme.layout_window` for the current homes.
4. `qt/host.py`: `QtHost`, what the Qt tabs read instead of the Tk window. It holds the `Controls` from `app_controls.make_controls` and exposes its fields as attributes under the same names (so tab code reads `host.on_toggle_ntfy` as Tk reads `win.on_toggle_ntfy`), plus the Qt-only seams: `state_dir` (the Accounts tab reads it, `settings_accounts.py:73`), `panes`, `always_on_top()` (a wrapper: the widget's `always_on_top` is a property, `qt/widget.py:517`) and `toggle_always_on_top()` (calls `widget.set_always_on_top(not widget.always_on_top)`), `theme()` and `set_theme(theme)` (saves `theme.json` through `theme.save_theme`, then `widget.set_theme`), `pane_color(index, field)` (coat colours from the pane palette `o`/`O`; `card_bg` is the effective card colour, the override if set, else the theme's `card.background`, which is what the widget paints and what Tk's `pane._card_bg` holds; `bar_fill` from the overrides, `None` when unset, which the tab shows as automatic, as `settings_ui._pane_color` does), `notify_state_changed()` (refreshes an open Settings window; no tray until #114), `on_layout_changed(pane_index, custom)` (the spec's adapter: `pane.set_customization(custom)`, then every pane's `theme.resolve_home`, then `widget.rebuild_layout(homes)` only when the homes changed; `Controls` calls it after every customization save and sets a changed label itself through `apply_customization` and `initial_label`, `app_controls.py:107-113`, so the adapter must not touch the label), `warn(title, text)` (`QMessageBox.warning` parented to the asking window), and the opener seams slices 3 and 5 fill (`on_open_accounts`, `on_edit_streamdock_presets`), `None` until then. The tray and update seams stay `None`, which hides their rows exactly as the Tk tabs do.
5. Stacking: `QtHost` keeps a list of the top-level windows it opened. `toggle_always_on_top()` flips the widget, then for each open window sets or clears `WindowStaysOnTopHint` with `setWindowFlag` and re-shows it (a flag change hides the window). Each window gets the hint at creation when the widget is in front.
6. `qt/settings.py`: `SettingsWindow.open(host, pane_index)`, a port of `settings_ui.SettingsWindow` and its General, Look and Usage tabs (read `settings_ui.py` whole). Parentless `QWidget`, title "Tokitty: Settings", minimum size `BASE_WIDTH` by `BASE_HEIGHT`, grown to the tallest tab, rail, scroll area, footer with Close. One instance per `QApplication` (module-level), reopening switches the pane and raises. `_Tab.write(action)` runs the seam, then `host.notify_state_changed()`. Tab order General, Look, Theme, Usage (Accounts and Stream Dock arrive in slices 3 and 5; build the rail from a list so they slot in). Differences from Tk, all from the spec: General has no Transparency row and shows Start at login only when `host.autostart_enabled` is set; Look reads colours through `host.pane_color` and writes through `host.on_customization_changed`; Look gains Cat sits (Left, Right, and On top only for a first-row pane, from `theme.resolve_home(spot, index, count) == spot`) writing `"cat_home"`; colour rows use `QColorDialog.getColor(parent=settings_window)`.
7. Theme tab, in `qt/settings.py`: the controls in the spec's "Theme tab" section. Each edit starts from `current = host.theme()` (a `Theme`), builds `raw = theme.theme_to_dict(current)` with the one edited key changed, and runs `theme.rejected_fields(raw, current)`, whose names are `"section.field"` (`"card.opacity"`); the fallback argument of both functions is the `Theme`, never the dict. If the edited key is rejected, mark the entry with `set_entry_error` and keep the old value; otherwise `host.set_theme(theme.theme_from_dict(raw, current))`. Mid from and High from at or above each other mark both. Opacity is a segmented row 0 to 100 by 10; at 0 an inline hint reads "You'll need to right-click where the widget is to get back here" (Nick, 2026-10-12). Reset theme writes `theme.Theme()`.
8. `qt/app.py`: two-phase setup, because `Controls` needs host methods and the host needs `Controls`. Create `QtHost(widget, state_dir)` first, then `controls = make_controls(state_dir, units, usage_state, customization_store, settings, apply_customization=..., on_layout_changed=host.on_layout_changed, distro_probe=distro_probe, deck_fn=lambda: None, label_fn=lambda i: widget.panes[i]._label if i < len(widget.panes) else None, warn=host.warn)` (the real signature, `app_controls.py:60`; there is no `discovery` parameter), then `host.attach(controls)`. `apply_customization(pane, custom)` sets the pane's appearance from the customization as `run_gui`'s does, minus the Tk default colour. Then pass `on_open_settings=lambda: SettingsWindow.open(host, pane_index)` to `build_menu` in `menu_model(pane_index)`, point the widget's `on_menu_action_done` at `host.notify_state_changed`, apply the surprise-me randomize at startup as `run_gui` does, and call `QApplication.setQuitOnLastWindowClosed(False)` right after the `QApplication` is created (spec, "First-run walkthrough", step 3, and the measured reason). On macOS, the `QMenuBar` with a menu holding a Settings action with `PreferencesRole`, created before the widget is shown and kept referenced for the life of the app.
9. Tests (`tests/qt/test_settings.py`), from the spec's Settings and Theme bullets (Theme checks assert the saved `Theme` and the widget's state; pixel samples only on card and bar areas, never on text, since offscreen Qt on Windows draws no glyphs), plus: closing Settings with the widget shown leaves the event loop running (open, close, then a `QTimer` checks `app` is still executing and quits it); toggling always in front sets and clears the hint on an open Settings window; the debug launch still writes nothing but the lock (existing test keeps passing).
